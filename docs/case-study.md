# Case study: 儿童 AI 教育互动内容系统

## 项目概览

| 项目 | 内容 |
| --- | --- |
| 产品形态 | Web + 微信小程序的儿童 AI 教育互动内容原型 |
| 核心系统 | AI 预设主动提问、用户打断提问、儿童互动记忆 |
| 教育框架 | 大语文、百科知识、文化理解、逻辑思维、情绪理解、想象力、语言表达 |
| 核心产出 | 问题设计体系、Question Planner、Memory Layer、状态机、跨端界面、证据报告 |
| 公开演示 | Mock provider + Browser SpeechSynthesis + 文字模拟 ASR |
| 完整原型 | Streaming ASR + LLM SSE + 并发 Streaming TTS + PCM 播放 |
| 当前阶段 | 流式工程链路已跑通；尚未完成真实儿童研究与生产级安全、部署验证 |

## 1. 产品重新定义

如果把 StoryPal 描述为“可以打断的语音故事机”，产品价值会被压缩成输入输出形式。真正的产品问题包括：

1. AI 应该在什么情节位置主动提问；
2. 问题希望支持儿童哪一种理解或表达；
3. 孩子不主动表达时，怎样用脚手架降低门槛；
4. 孩子产生真实问题时，怎样及时进入对话；
5. 两类互动如何使用不同的恢复规则；
6. 多轮互动如何利用记忆保持连续并减少重复；
7. 家长如何看到真实证据，同时不被伪能力评分误导。

项目因此从“语音交互”扩展为教育内容、双交互、记忆、AI 回应和家长证据的完整系统。

## 2. 产品差异：教育目标进入 Workflow

StoryPal 的竞争力不建立在“能讲故事”或“能语音聊天”两个通用能力上。核心产品资产包括：

1. **教育内容模型**：每个互动点都有情节触发理由、七维目标、问题类型、学习目标、脚手架、追问与略过规则；
2. **双交互机制**：AI 主动引导解决“儿童不主动问”的问题，用户打断保护好奇心与自主表达；
3. **策略受控**：Planner 从人审候选中选择，LLM 不负责临场制定教学目标；
4. **适龄回应**：先回应问题，再连接故事证据，必要时用一个脚手架帮助儿童继续表达；
5. **教育记忆**：Memory 服务问题去重、上下文连续和证据组织，不以塑造陪伴人格为主要目的；
6. **事实型报告**：家长看到儿童说了什么、系统如何回应、覆盖什么维度，不看到缺乏证据的“情商分”“逻辑分”；
7. **教育节奏工程**：预制故事音频、低延迟实时回答和原句恢复用于保护沉浸与工作记忆。

因此，模型能力只是系统的一层。即使替换 LLM，问题设计、教育策略、记忆边界、双交互规则和报告证据链仍然成立。

## 3. 原项目能力还原

公开版升级前，我重新核查了原 StoryPal 原型中的真实设计：

- `guided` 与 `interrupt` 是两条不同交互路径；
- 内容生产规范要求每个故事设置 2–4 个主动互动点；
- 互动点位于选择、因果、情绪、知识和创意表达等剧情自然停顿处；
- capability schema 包含七个教育维度；
- Prompt 会先判断儿童是在问知识、聊情绪、展开想象、分析原因还是关注语言文化；
- Light Memory 保存基础画像、维度互动证据和近期短记忆；
- 原报告已有维度展示方向，但部分简化评分缺乏足够证据。

公开作品集保留了这些产品深度，同时把记忆和报告改成更安全的 session evidence 模型。

## 4. 核心方案

### 教育内容层

`story node` 承担叙事，`proactive_question node` 承担主动问题。每个问题候选包含主/副维度、问题类型、学习目标、触发原因、脚手架和追问策略。

### AI 主动提问模块

Question Planner 从审核过的问题池中选择问题，使用 session memory 的维度覆盖减少重复。模型不临场决定教学目标。

### 用户打断提问模块

孩子可在任意故事句暂停。Provider 使用当前句和近期互动回答，StorySession 保留游标并在回答后重播原句。

### 儿童互动记忆

SessionMemory 保存模块来源、儿童表达、AI 回应、情节上下文、教育维度和输入分类。它服务于问题选择、连续回应和证据报告，不产生能力或心理诊断。

## 5. 主要产品取舍

### 取舍 A：预设问题池＋Memory 选择

完全由模型生成问题具有灵活性，但教育目标、难度和安全边界不稳定。完全固定单题容易机械重复。公开版采用经过审核的候选池，再由 Memory-aware Planner 调整优先级。

### 取舍 B：七维框架不等于七维评分

维度用于设计问题和组织互动证据。一次对话不足以形成稳定能力结论，因此报告只显示维度覆盖和原始证据。

### 取舍 C：Session Memory 优先

跨会话画像能提高个性化，但涉及儿童隐私、监护人同意和错误推断。公开版只实现进程内 session memory，并提供立即删除接口。

### 取舍 D：按句恢复

按句恢复牺牲了句内时间戳精度，但能跨 TTS provider 保持稳定，也便于内容编辑、测试和解释。

### 取舍 E：Backend 管理游标

两个客户端各自管理权威进度会产生漂移。Backend 统一保存 `node_index + sentence_index`，客户端只上报播放完成和用户意图。

### 取舍 F：Mock-first 公开演示

确定性 Mock 让招聘方无密钥复现 Question Planner、Memory 和双模块闭环。它验证产品编排，不把模型效果包装成产品成绩。

### 取舍 G：原创内容与安全公开

公开版移除第三方故事、封面、录音、真实 AppID 和供应商配置，改用原创故事、CSS 视觉和占位配置。

## 7. 已完成验证

自动化测试覆盖：

- 完整走完两个 AI 主动提问节点；
- 用户打断后回到相同 node 和 sentence；
- 主动问题与打断问题进入不同 report module；
- Planner 根据历史维度选择尚未覆盖的问题；
- Session Memory 包含近期事实但不包含能力分数；
- 主动问题可以略过；
- Memory Repository 支持立即删除；
- 非法 command 顺序被拒绝；
- 完整故事、维度覆盖和报告生成。

端到端验证计划还包括 REST、真实 WebSocket、浏览器界面和匿名 GitHub 可访问性。上述验证支持“产品逻辑和代码可运行”，不支持“提升儿童阅读效果”等结论。

## 8. 工程难点与解决路径

### 难点一：低延迟不能只优化模型响应

儿童感受到的等待由停播反馈、VAD、ASR、上下文准备、LLM、审核、TTS 和播放缓冲共同组成。只比较模型首 token 会遗漏主要瓶颈。

解决路径是把串行链路改成流水线：前端本地停播；session 内复用麦克风与 AudioWorklet；Streaming ASR 返回结果；LLM 以 SSE 增量生成；SmartBuffer 一旦得到可播句就启动最多三路并发 Streaming TTS；sender queue 按句序下发 PCM，客户端通过 200ms jitter buffer 边收边播。故事正文和主动问题使用预生成或首播缓存。

24 轮保留日志中，LLM 首 token 为 `min 431ms / p50 590ms / p90 797ms / max 999ms`。日志也证明首音频早于完整回答结束。现有首音频事件没有统一 elapsed 字段，因此没有把 `<1.5s` 写成已测 SLA；这体现了指标口径的克制。

### 难点二：回答越快，流式安全越难

逐 token 播放可以获得最低延迟，但儿童已经听到的错误或不适当内容无法撤回。现有实现用 SmartBuffer 在语义边界后启动 TTS，解决了“token 不能直接合成”的问题，还没有独立的安全审核 Gate。上线方案应以完整句作为最小审核单元：普通问题保留一句缓冲，高风险问题等待完整审核或返回安全模板。

### 难点三：打断是分布式状态问题

客户端在播放音频，Backend 持有故事游标，ASR、LLM 和 TTS 又可能继续产生迟到结果。完整原型已经加入 `turn_id`、`client_interaction_id`、本地立即清队列和旧音频 discard window，并改为上报真实起播的 `node_id + sentence_index`。剩余风险是原始二进制音频帧没有携带 `response_id`，还需要协议化取消、幂等 command 和重连策略。

### 难点四：连续感、成本和隐私同时约束上下文

发送完整故事和完整历史容易增加延迟与 token，也扩大儿童数据暴露。完整原型在 WebSocket session 建立时 preload 轻量记忆，只选择少量相关 note 进入 Prompt，并把互动后的磁盘更新放到回答结束后的后台线程。公开版进一步收紧为当前句、Question Plan 和最近三条 session interaction。

### 难点五：分句速度与听感存在直接冲突

每出现一个标点就启动 TTS 可以更快出声，但会产生过多连接、短音频碎片和拼接感；等待更长句子能改善听感，却会拖慢首段。项目实现了 SmartBuffer、首短语抢跑、三路 TTS 并发和按句序发送。后续审计发现 30 字合并阈值对短回答过于保守，合理改进是“最小语义单元＋200–300ms 最大等待时间”，而非只看字符数。

### 难点六：回答效果没有单一指标

“听起来流畅”不能代表事实正确、儿童听得懂或具有教育价值。评估需要同时覆盖：

- 性能：首段延迟、完整耗时、超时率、恢复成功率；
- 回答：相关性、故事事实一致性、年龄可理解性、重复率；
- 安全：风险召回、误拦截、降级成功率；
- 互动：儿童继续表达率、略过率、回答被二次打断率；
- 教育：问题是否触发目标行为，只记录证据，不输出能力诊断。

## 9. 回答效果与延迟的产品取舍

| 场景 | 方案 | 取舍 |
| --- | --- | --- |
| AI 主动提问 | 人工审核候选＋Planner＋预生成语音 | 灵活性有限，但时机、目标、安全和延迟稳定 |
| 简单情节问题 | 当前 node 事实＋低延迟模型 | 缩短上下文，避免扩写无关知识 |
| 百科问题 | 事实包/检索＋模型组织语言 | 增加少量延迟，降低编造风险 |
| 想象与表达 | 开放回应＋一个追问 | 不设唯一答案，控制回答长度 |
| 情绪或敏感问题 | 风险升级＋完整审核/安全模板 | 安全优先于首段速度 |
| 供应商超时 | 短模板＋恢复故事 | 不让儿童停留在无反馈状态 |

默认回答设计为 2–4 句：先直接回应，再连接故事证据，必要时给一个低压力追问。它既降低首段等待，也控制 AI 抢占故事主体的问题。

## 10. 关键工程架构决策

1. Backend 持有权威游标，客户端只上报意图和播放事实；
2. 双交互共用状态机，但使用不同的上下文、教育维度来源与恢复规则；
3. WebSocket 统一 Web 与小程序协议，生产版再增加序号、ack、幂等与重连；
4. 内容 schema、Question Planner、Memory、Provider 相互分层，供应商可替换；
5. 主动问题采用人审候选，模型负责受控回应，不临场制定教学目标；
6. Memory 默认 session-only，并限制读取窗口；
7. 恢复粒度选择句级，优先保证跨端稳定和可测试；
8. 公开版坚持 Mock-first，保留可复现性并诚实暴露生产差距；
9. 完整原型采用“预生成叙事音频＋实时互动回答”的 Hybrid Architecture，把稳定听感与开放交互分开优化；
10. TTS 选择“并发生成＋按序发送”，将吞吐优化与语义顺序解耦；
11. 客户端主动增加 200ms jitter buffer，用可控延迟换取公网连续播放。

## 11. 当前不足

- 公开仓库没有真实 ASR、LLM、TTS adapter；完整原型已有实现，但尚未完成脱敏后的通用 adapter 整理；
- 没有儿童和家长用户研究记录；
- 小程序尚未完成公开版真机验证；
- Memory 仅为 session-only；
- 没有完整监护人同意、导出和自动过期；
- 流式模型输出尚未接入独立的句级内容安全 Gate；
- 首音频事件已有埋点，但缺少统一 elapsed 字段和自动化延迟报表；
- 二进制音频帧尚未携带 `response_id`，旧音频失效主要由客户端窗口控制；
- 目前只有一个原创故事，无法验证内容规模化；
- 没有演示视频和跨端真机截图。

## 12. 下一阶段优先级

### P0：验证双交互与问题设计

- 观察儿童能否区分 AI 主动提问和自由打断；
- 测试 2–4 个主动问题对沉浸感的影响；
- 验证七维问题在不同年龄段的理解难度；
- 测试“脚手架后表达率”和略过率；
- 完成微信开发者工具与真机验证。

### P1：把已跑通的流式链路产品化

- 把供应商 adapter 整理为可替换的 streaming contract；
- 用统一 monotonic clock 补齐 endpoint-to-first-audio 指标；
- 为音频帧增加 `response_id`，完善取消、背压和 timeout；
- 增加 Guardrailed LLM、事实包、句级审核和断网降级。

### P2：建立监护人和记忆治理

- 监护人同意、Memory 查看、纠正、导出、删除和关闭；
- TTL、用途范围、来源与审计；
- 严格区分儿童原话与系统推测；
- 禁止未经同意的跨会话画像。

### P3：内容规模化

- 问题设计卡和故事 node 编辑工具；
- 七维问题模板、人工审核和版本管理；
- 故事库维度分布与重复率分析；
- 不同互动密度和问题类型的实验。

## 13. 这个项目体现的能力

- 把“AI 陪伴阅读”拆解成教育内容、双交互、记忆和安全报告；
- 让教育目标进入内容 schema、Planner、状态机、Memory 和报告，而非只写进 Prompt；
- 将儿童心理与教育维度落实为问题 schema、脚手架和内容规则；
- 识别模型调用之外的状态、恢复、略过、记忆与证据问题；
- 把内容结构、产品规则、协议、多端 UI 和测试对齐；
- 用 Question Planner 和 Provider contract 保留策略与供应商扩展空间；
- 把 ASR、LLM、TTS 串行等待改成可观测的流式 Pipeline，并通过分句并发、有序队列和客户端缓冲平衡延迟与听感；
- 能识别“已实现低延迟”与“已建立严格 SLA”的证据差别，主动暴露指标和协议欠账；
- 借助 AI Coding 完成端到端原型和公开工程化；
- 明确区分已实现能力、产品假设与生产化规划。
