# Case study: 从有声播放到可恢复的 AI 对话工作流

## 项目概览

| 项目 | 内容 |
| --- | --- |
| 产品形态 | Web + 微信小程序的 AI 互动阅读原型 |
| 核心场景 | 儿童听故事时主动打断、提问、获得语境回答并继续收听 |
| 核心产出 | 产品逻辑、状态机、统一协议、跨端界面、互动报告、公开工程化 |
| 公开演示 | Mock provider + Browser SpeechSynthesis + 文字模拟 ASR |
| 当前阶段 | 可运行作品集原型，尚未进行真实儿童与生产模型验证 |

## 1. 问题拆解

“给故事播放器加 AI 问答”表面上是模型调用，真正影响体验的是五个流程问题：

1. 什么时候允许孩子进入对话；
2. 对话时故事播放如何停止；
3. AI 回答需要多少故事上下文；
4. 回答后从哪里继续；
5. 互动记录如何呈现且不过度解释。

如果这些问题交给前端临时判断，不同端容易出现并发播放、重复回答、进度漂移和错位续播。因此，项目把重点放在产品状态和事件协议上。

## 2. 核心方案

方案由四部分组成：

- 用 `story node + interaction node` 把叙事和预设互动放在同一内容序列；
- 用 `node_index + sentence_index` 保存可恢复的最小故事游标；
- 用 `idle / playing / awaiting_input / answering / ended` 描述互斥状态；
- 用 `CompanionProvider` 隔离产品逻辑与具体模型供应商。

主动打断和预设引导共用回答链路，但主动打断回到原句，预设引导进入下一 node。这一差异是整个产品闭环的关键。

## 3. 主要产品取舍

### 取舍 A：按句恢复，而非精确音频时间戳

选择按句，是为了让内容模型、TTS provider 和客户端保持低耦合。它牺牲了句内的精确恢复，但获得稳定、可解释且容易验证的行为。

### 取舍 B：Backend 管理游标，而非客户端管理

客户端更了解本地播放状态，但两个端分别持有权威游标会产生行为差异。Backend 统一游标后，客户端只需报告播放完成和用户意图。

### 取舍 C：Mock-first 公开演示

公开版目标是让招聘方和开发者无密钥复现产品闭环。确定性 Mock 便于测试和理解，也诚实暴露“尚未验证模型效果”的边界。真实 provider 可以按 contract 接入，但不作为公开版能力宣称。

### 取舍 D：报告呈现事实，不生成能力分数

儿童内容产品容易把一次对话包装成成长分析。当前证据只支持展示进度和互动时间线，因此报告保持克制，避免伪精确结论。

### 取舍 E：公开仓库使用原创内容和 CSS 视觉

公开作品集移除第三方故事、封面、录音、真实 AppID 和供应商配置，改用原创故事与 CSS/emoji 视觉。仓库因此可以安全公开和复现。

## 5. 已完成验证

### 自动化验证

- 主动打断后回答，并确认恢复到同一个 node 和 sentence；
- 完整走完故事和两个引导互动；
- 校验完成报告的状态、进度和互动次数；
- 拒绝未开始就发送 `sentence_complete` 的非法顺序。

### 端到端验证

- 启动 FastAPI 本地服务；
- 检查健康与故事目录 API；
- 用真实 WebSocket 走通开始、打断、输入、回答和原句恢复；
- 在浏览器检查首页、播放器和公开仓库呈现；
- 匿名确认 GitHub 仓库公开、MIT License 可识别。

这些验证支持“流程可运行”的结论，不支持“真实儿童喜欢”“模型回答质量达标”或“提升阅读效果”等结论。

## 6. 当前不足

- 没有真实 ASR、LLM、TTS 的公开 adapter；
- 没有儿童和家长用户研究记录；
- 微信小程序尚未在开发者工具和真机完成公开版验证；
- session 与报告只保存在内存；
- 没有模型安全、监护人同意和数据删除的完整实现；
- 没有演示视频和跨端真实截图；
- 目前只有一个原创故事，无法验证内容运营和规模化生产流程。

## 7. 下一阶段优先级

### P0：验证核心体验

- 在受控条件下完成微信开发者工具验证；
- 接入一个可中断 TTS 和一个带置信度的 ASR adapter；
- 观察儿童是否理解打断入口和原句恢复；
- 验证回答延迟是否破坏故事连续性。

### P1：建立安全与监护人闭环

- 监护人同意、会话查看、数据删除；
- 输入输出审核与模型超时降级；
- 报告口径评审和敏感信息处理；
- 账户隔离、WSS、限流和审计。

### P2：验证内容规模化

- 内容 node 编辑工具和版本管理；
- 引导问题模板与编辑准则；
- 多故事目录和主题运营；
- 比较不同互动密度对完成率与表达率的影响。

## 8. 这个项目体现的能力

- 把模糊的“AI 陪伴阅读”拆成可验证的产品闭环；
- 识别模型调用之外的状态、恢复、错误和报告问题；
- 把内容结构、产品规则、协议和多端 UI 对齐；
- 用 provider contract 保留供应商替换空间；
- 借助 AI Coding 完成端到端原型、测试和公开工程化；
- 在公开作品集中明确区分已实现、设计方案与生产化规划。
